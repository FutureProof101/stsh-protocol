> **DEF-111 / B-prime — value-bound Merkle leaf.** The tree leaf is
> `MerkleLeaf = Poseidon(3)[value, inner_note_commitment, MERKLE_LEAF_DOMAIN=4]`
> (t=4, purpose tag last), NOT the raw inner commitment. `domain_sep` is omitted from
> the outer leaf (the inner commitment already binds it — the 0b ruling), keeping
> arity at Poseidon(3). This is computed on BOTH sides: the circuit `MerkleLeaf`
> template and `stsh_field_utils::merkle_leaf` (fixed t=4 params in
> `canisters/field-utils/src/poseidon_params.rs`, generated verbatim from
> light-poseidon 0.2.0 `get_poseidon_parameters(4)` — never `new_circom`, to stay
> under the IC Wasm function-complexity ceiling). The internal Merkle **node** hash
> (`Poseidon(2)`, t=3) is unchanged; the leaf is a different, wider hash.
> Leaf-agreement is guarded byte-for-byte by
> `test_merkle_leaf_agrees_with_circomlib_vector`. On deposit the leaf binds the
> CREDITED value, which under the **fee-ON-TOP** model is the **full gross**:
> `private_balance_credit = gross_shield_amount` — **not** reduced by the fee
> (`canisters/shielded-pool/src/lib.rs`, the `shield_deposit` fee-ON-TOP identity block — cite by anchor text `private_balance_credit = gross_shield_amount`, not line). The depositor transfers
> `gross_shield_amount + protocol_shielding_fee`; the fee is charged on top and
> credited to the protocol reserve, and the leaf binds the full gross, which is
> the same amount booked to `PRIVATE_LIABILITY`.
>
> **This corrects a superseded fee-DEDUCTED statement (AR1-10).** The distinction is
> load-bearing rather than editorial: the pool computes the outer leaf itself, and an
> implementer who binds `gross − fee` inside a leaf the pool binds at `gross`
> produces a note that can **never be spent** — the circuit derives both from one
> `in_value`, so no error is raised anywhere and the tokens sit in escrow. Our own
> wallet is correct, so nothing is live; the exposure was to anyone implementing
> against this document, which is what it is for.
>
> Updated post-DEF-035 + DEF-109-A: nullifier uses `Poseidon(4)[domain_sep, spend_key, in_commitment,
> NULLIFIER_DOMAIN=2]`; note commitment uses `Poseidon(6)[domain_sep, value,
> recipient_pk, rho, rseed, COMMITMENT_DOMAIN=3]`; the cross-deployment `domain_sep`
> is itself `Poseidon(4)[DOMAIN_POOL_CANISTER_ID, DOMAIN_ASSET_ID,
> DOMAIN_CIRCUIT_VERSION, DOMAIN_NETWORK_ID]`. PK derivation is unchanged —
> `Poseidon(2)` with `PK_DOMAIN=1`, NOT domain-separated. See the
> "Domain Separation (DEF-035)" section below.
> (Pre-DEF-035 this table listed Nullifier = Poseidon(3) / Commitment = Poseidon(5).)

## Field

BN254 scalar field **Fr**

```
Order p = 21888242871839275222246405745257275088548364400416034343698204186575808495617
        = 0x30644e72e131a029b85045b68181585d2833e84879b9709143e1f593f0000001
```

All field elements fit in 254 bits and are stored as 32-byte little-endian arrays.

## Poseidon variant — circomlib standard

| Parameter       | Value                                                     |
|-----------------|-----------------------------------------------------------|
| Variant         | circomlib Poseidon (Grassi et al., 2019; iden3 reference) |
| State width t   | 3  (= arity + 1 = 2 + 1)                                 |
| Full rounds RF  | 8                                                         |
| Partial rounds RP | 57  (for t = 3 over BN254)                             |
| Round constants | circomlib `poseidon_constants.circom` (generated by iden3 reference script) |
| MDS matrix      | circomlib standard for t = 3 over BN254                   |
| Permutation     | Poseidon-π as in the original Grassi et al. paper         |
| S-box           | x^5 (full rounds), x^5 on one element (partial rounds)   |

**Rust crate:** `light-poseidon = "0.2"`
**Configuration:** the fixed t=3 parameter set `poseidon_params::fixed_poseidon_t3_params()`
(`canisters/merkle-tree/src/poseidon_params.rs`), generated verbatim from light-poseidon 0.2.0
`new_circom(2)`; `new_circom` itself is test-only (Wasm function-complexity ceiling — same rule
as the DEF-111 leaf note above).

## Hash function for Merkle tree nodes

```
hash_pair(left, right) = Poseidon([left, right])
```

**Input ordering** — left then right — matches the MerkleProof Switcher in
`circuits/spend.circom`:

```circom
hashers[i].inputs[0] <== switchers[i].outL;   // left child
hashers[i].inputs[1] <== switchers[i].outR;   // right child
```

When `path_index[i] == 0`, the current node is on the left; sibling is on the
right.  When `path_index[i] == 1`, the sibling is on the left; current node is
on the right.  The Switcher handles re-ordering so `inputs[0]` is always the
left child of that level.

## Byte encoding

Fr field elements are encoded as **little-endian** 32-byte arrays throughout:

- `ark_ff::PrimeField::from_le_bytes_mod_order(&bytes)` — bytes → Fr
- `field.into_bigint().to_bytes_le()` — Fr → bytes

**All callers must use the same encoding:**

- Rust canister (`canisters/merkle-tree`) — ✓ (this implementation)
- Wallet frontend (`wallet/src/crypto/notes.ts`, `bigintToFieldLe`) — ✓ (leaf-agreement checkpoint, BINDING §4.3)
- Integration tests — ✓ (use raw bytes; no conversion needed for unit tests)
- snarkjs proof output — public inputs as decimal Fr strings; wallet must convert
  to little-endian bytes before passing the anchor to `is_valid_anchor()`

## Zero values

The canonical zero values for a depth-32 Merkle tree are:

```
ZERO_VALUES[0]   = Poseidon(Fr::zero(), Fr::zero())
ZERO_VALUES[i]   = Poseidon(ZERO_VALUES[i-1], ZERO_VALUES[i-1])  for i in 1..=32
ZERO_VALUES[32]  = canonical Poseidon empty-tree root
```

Computed in Rust by `compute_zero_values_raw()` in `canisters/merkle-tree/src/lib.rs`.
Stored as a `thread_local! { static ZERO_VALUES: [[u8; 32]; 33] }`.

**Key security property:** `[0u8; 32]` does NOT appear anywhere in `ZERO_VALUES`.
`is_valid_anchor([0u8; 32])` returns `false` on any correctly initialised
post-M4 canister.  Verified by integration test `test_54`.

### Printed values

The actual 33 hex-encoded zero values are output by the unit test
`test_print_zero_values` in `canisters/merkle-tree/src/lib.rs`.  Run:

```bash
cargo test -p merkle_tree test_print_zero_values -- --nocapture
```

Cross-check these against the circomlib JavaScript reference:

```javascript
// node_modules/circomlib/src/poseidon_reference.js
const { poseidon } = require("circomlib");
const F = require("ffjavascript").bn128.Fr;

let z = [F.zero];
for (let i = 0; i < 33; i++) {
  z.push(poseidon([z[z.length-1], z[z.length-1]]));
}
// z[0] = Poseidon(0, 0)  (first entry is Fr.zero before hashing — shift by 1)
```

## Domain Separation (DEF-035)

Cross-deployment domain separation (QA-DEF-035): a deployment-binding domain
separator is embedded in the Poseidon preimage of the nullifier and every note
commitment, as the **first** input. This binds every proof to a specific deployment
so a valid proof generated for one STSH deployment cannot be replayed on another
that shares the same verifying key.

```
domainHash = Poseidon(4)[DOMAIN_POOL_CANISTER_ID, DOMAIN_ASSET_ID,
                         DOMAIN_CIRCUIT_VERSION, DOMAIN_NETWORK_ID]

nullifier  = Poseidon(4)[domainHash, spend_key, in_commitment, NULLIFIER_DOMAIN]   // DEF-109-A: full-note binding
commitment = Poseidon(6)[domainHash, value, recipient_pk, rho, rseed, COMMITMENT_DOMAIN]
```

Finalized values — circuit-finalization revision (DEF-082, Stage 1 of 3). Circuit
constants, NOT public signals:

```
DOMAIN_POOL_CANISTER_ID = 4523128485832663883733241601901871400518358776001584537546685574107874983936
                              (MAINNET — cxrfg-qaaaa-aaaar-qchfa-cai, the Vault-born pool;
                               re-encoded at A-3 FINALIZE 2026-09-12 for generation mainnet-v2.
                               The A1 value (ohspu-zqaaa-aaaad-qmasq-cai, injected 2026-07-07)
                               and the pre-A1 staging sentinel 2 are both historical.)
DOMAIN_ASSET_ID         = 0   (STSH native token — FINAL)
```
